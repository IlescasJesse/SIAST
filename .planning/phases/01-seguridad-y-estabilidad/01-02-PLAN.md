<objective>
Completar el hardening de auth: instalar y configurar rate limiting en todos los endpoints de autenticación, eliminar el endpoint legacy login-rfc y su referencia en el frontend, y corregir el token refresh para que verifique revocación de sesión antes de emitir un nuevo token.

Purpose: Sin rate limiting, los OTPs de 6 dígitos son bruteforce-ables en 1M intentos sin restricción. Sin verificación de sesión en refresh, un usuario desconectado puede seguir obteniendo tokens nuevos indefinidamente. El endpoint legacy login-rfc bypass el flujo OTP completo usando solo el RFC (que es información semi-pública).

Output: Rate limiter activo en los 4 endpoints de auth. Endpoint /api/auth/login-rfc eliminado. Método loginRFC eliminado del store. refreshToken verifica que la sesión no fue revocada antes de emitir el nuevo token.
</objective>

```typescript
export async function verificarSesion(jti: string): Promise<boolean> {
  const sesion = await prisma.sesion.findUnique({
    where: { jti },
    select: { activa: true, expiresAt: true },
  });
  if (!sesion || !sesion.activa) return false;
  if (sesion.expiresAt < new Date()) {
    await prisma.sesion.update({ where: { jti }, data: { activa: false } });
    return false;
  }
  return true;
}
```

**Crear el archivo apps/api/src/middleware/rate-limit.middleware.ts:**

```typescript
import { rateLimit } from "express-rate-limit";

/**
 * Rate limiter para endpoints de autenticación.
 * 5 intentos máximo por IP en una ventana de 15 minutos.
 * SEC-04: protección contra brute-force de OTP y contraseñas de staff.
 */
export const authRateLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutos
  limit: 5, // 5 intentos por IP (usar "limit", no "max" — renombrado en v7+)
  standardHeaders: "draft-8", // Emite header RateLimit estándar IETF
  legacyHeaders: false, // No emitir X-RateLimit-* headers legacy
  message: { error: "Demasiados intentos. Intenta en 15 minutos." },
});
```

**Importante:** En express-rate-limit v7+, el option se llama `limit` (no `max`). Usar `max` silenciosamente usa el default de 100 sin error.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → /api/auth/* | Endpoints de autenticación sin auth previo — accesibles por cualquier cliente |
| refreshToken → sesiones DB | El refresh debe verificar que la sesión sigue activa en DB |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | POST /api/auth/solicitar-otp | mitigate | Brute-force de OTP (6 dígitos = 1M combinaciones) sin restricción de rate. Mitigación: express-rate-limit 5 req/15min por IP con `limit: 5` (no `max`) en v8.x |
| T-02-02 | Elevation of Privilege | POST /api/auth/login-rfc | mitigate | El endpoint bypasea el flujo OTP — cualquier RFC (información semi-pública) permite login. Mitigación: eliminación completa de la ruta del router y del método del store |
| T-02-03 | Repudiation | POST /api/auth/refresh | mitigate | Token refresh emite nuevo JWT sin verificar si la sesión fue revocada por logout o admin. Mitigación: verificarSesion(payload.jti) antes de signToken — si sesión inactiva → 401 |
| T-02-04 | Spoofing | apps/api/src/controllers/auth.controller.ts | mitigate | Fallback duplicado JWT_SECRET en refreshToken — misma vulnerabilidad de sec T-01-01 pero en archivo diferente. Mitigación: eliminar `process.env.JWT_SECRET ?? "siast_dev_secret"` de esta función |
</threat_model>
